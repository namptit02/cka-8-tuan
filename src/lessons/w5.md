# L: Volume, PV, PVC, StorageClass

## Volume trong Pod
| Loại | Sống bao lâu | Dùng khi |
|---|---|---|
| `emptyDir` | theo pod | chia sẻ file giữa các container, cache |
| `hostPath` | theo node | đọc file trên node (log, socket); tránh cho app thường |
| `configMap` / `secret` | theo object | file cấu hình |
| `persistentVolumeClaim` | độc lập với pod | dữ liệu bền vững |

## PV, PVC, StorageClass
- **PersistentVolume (PV)**: một mảnh lưu trữ thật (NFS, disk cloud, local). Không thuộc namespace.
- **PersistentVolumeClaim (PVC)**: "đơn xin" lưu trữ của ứng dụng: cần bao nhiêu, kiểu truy cập gì. Thuộc namespace.
- **StorageClass (SC)**: mẫu để **tự tạo PV** (dynamic provisioning) khi có PVC.

PVC **bind** với PV khi: storageClassName khớp, accessModes khớp, dung lượng PV ≥ yêu cầu (và selector nếu có). Một PV chỉ bind với một PVC.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata: {name: pv1}
spec:
  capacity: {storage: 1Gi}
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath: {path: /mnt/data}
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: pvc1}
spec:
  storageClassName: manual
  accessModes: [ReadWriteOnce]
  resources: {requests: {storage: 500Mi}}
---
# trong Pod
volumes:
- name: data
  persistentVolumeClaim: {claimName: pvc1}
```

## Thuộc tính quan trọng
- **accessModes**: `ReadWriteOnce` (RWO, 1 node), `ReadOnlyMany` (ROX), `ReadWriteMany` (RWX, nhiều node – cần NFS/CephFS…), `ReadWriteOncePod` (RWOP, đúng 1 pod).
- **reclaimPolicy**: `Retain` (xoá PVC → PV thành `Released`, dữ liệu còn, phải dọn tay), `Delete` (xoá luôn PV và disk). PV `Released` muốn dùng lại: xoá `spec.claimRef`.
- **volumeBindingMode** của SC: `Immediate` hoặc `WaitForFirstConsumer` (đợi có pod dùng mới tạo/bind, tránh tạo disk sai zone/node). PVC Pending với WFFC khi chưa có pod là **bình thường**.
- **allowVolumeExpansion: true** → tăng dung lượng bằng cách sửa `spec.resources.requests.storage` của PVC (chỉ tăng, không giảm).
- SC mặc định: annotation `storageclass.kubernetes.io/is-default-class: "true"`. PVC không ghi `storageClassName` sẽ dùng SC mặc định; ghi `storageClassName: ""` để **không** dùng SC nào (chỉ bind PV tĩnh).

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-fast
  annotations: {storageclass.kubernetes.io/is-default-class: "true"}
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```
Lab tự dựng: cài `local-path-provisioner` của Rancher để có dynamic provisioning.

:::ex
Tạo PV `w5-pv` 2Gi, RWO, Retain, class `manual`, hostPath `/mnt/w5`. Tạo PVC `w5-pvc` 1Gi class `manual`. Tạo pod nginx mount PVC vào `/usr/share/nginx/html`, ghi file index.html, xoá pod, tạo lại pod và kiểm tra file còn.
:::sol
Dùng YAML trong phần lý thuyết (đổi tên, size). Sau đó:
```bash
kubectl get pv,pvc            # Bound
kubectl exec w5-pod -- sh -c 'echo persisted > /usr/share/nginx/html/index.html'
kubectl delete po w5-pod && kubectl apply -f w5-pod.yaml
kubectl exec w5-pod -- cat /usr/share/nginx/html/index.html    # persisted
```
Lưu ý hostPath: pod mới phải chạy trên **cùng node** thì mới thấy dữ liệu.
:::end

:::ex
Xoá `w5-pvc`. PV ở trạng thái gì? Làm sao để một PVC mới bind lại được PV đó?
:::sol
```bash
kubectl delete pvc w5-pvc      # (xoá pod dùng nó trước)
kubectl get pv w5-pv           # Released
kubectl patch pv w5-pv -p '{"spec":{"claimRef":null}}'
kubectl get pv w5-pv           # Available
```
:::end

:::ex
PVC `data` ở trạng thái Pending. Liệt kê 4 nguyên nhân thường gặp và lệnh kiểm tra.
:::sol
```bash
kubectl describe pvc data       # đọc Events
kubectl get pv ; kubectl get sc
```
1. `storageClassName` không tồn tại hoặc sai chính tả.
2. Không PV nào khớp accessModes/dung lượng (PV tĩnh).
3. SC dùng `WaitForFirstConsumer` và chưa có pod dùng PVC (bình thường).
4. Provisioner không chạy (pod provisioner lỗi), hoặc không có SC mặc định khi PVC không ghi class.
:::end

:::ex
Mở rộng PVC `w5-dyn` (dùng SC có `allowVolumeExpansion: true`) từ 1Gi lên 2Gi.
:::sol
```bash
kubectl patch pvc w5-dyn -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'
kubectl get pvc w5-dyn -w
```
:::end

# L: Xác thực, RBAC và ServiceAccount

## 3 bước khi gọi apiserver
1. **Authentication** – bạn là ai? (client certificate, token của ServiceAccount, OIDC). K8s **không có object User**; user là CN trong certificate, group là O.
2. **Authorization** – được làm gì? (RBAC, Node authorizer). Cờ `--authorization-mode=Node,RBAC` trên apiserver.
3. **Admission control** – sửa/chặn yêu cầu (LimitRange, ResourceQuota, PodSecurity…).

## RBAC – 4 object
| Object | Phạm vi | Vai trò |
|---|---|---|
| Role | namespace | tập quyền trong 1 namespace |
| ClusterRole | cluster | tập quyền toàn cluster, hoặc cho tài nguyên không thuộc namespace |
| RoleBinding | namespace | gắn Role (hoặc ClusterRole) cho user/group/SA **trong 1 namespace** |
| ClusterRoleBinding | cluster | gắn ClusterRole cho toàn cluster |

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {name: pod-reader, namespace: dev}
rules:
- apiGroups: [""]                    # "" = core (pods, services, secrets, configmaps)
  resources: [pods, pods/log]
  verbs: [get, list, watch]
- apiGroups: [apps]
  resources: [deployments]
  verbs: [get, list, create, update, patch, delete]
```
```bash
kubectl create role pod-reader -n dev --verb=get,list,watch --resource=pods,pods/log
kubectl create rolebinding rb -n dev --role=pod-reader --user=jane --group=devs --serviceaccount=dev:app-sa
kubectl create clusterrole node-viewer --verb=get,list --resource=nodes
kubectl create clusterrolebinding nv --clusterrole=node-viewer --user=jane
kubectl auth can-i list pods -n dev --as=jane
kubectl auth can-i '*' '*' --as=system:serviceaccount:dev:app-sa -n dev
kubectl auth can-i --list --as=jane -n dev
kubectl api-resources -o wide        # xem apiGroup và verbs của từng tài nguyên
```
Verbs: `get list watch create update patch delete deletecollection`. ClusterRole có sẵn: `view`, `edit`, `admin`, `cluster-admin`.

## ServiceAccount
Danh tính cho **process trong pod**. Mỗi namespace có SA `default`. Token được mount (dạng projected, có hạn) vào `/var/run/secrets/kubernetes.io/serviceaccount/token`.
```bash
kubectl create sa app-sa -n dev
kubectl create token app-sa -n dev --duration=1h      # cấp token tạm
kubectl set serviceaccount deploy/web app-sa -n dev   # gán cho deployment
```
```yaml
spec:
  serviceAccountName: app-sa
  automountServiceAccountToken: false     # không mount token nếu pod không cần gọi API
```

## Tạo user bằng certificate (CertificateSigningRequest)
```bash
openssl genrsa -out jane.key 2048
openssl req -new -key jane.key -out jane.csr -subj "/CN=jane/O=devs"
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata: {name: jane}
spec:
  request: $(base64 -w0 jane.csr)
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages: [client auth]
EOF
kubectl certificate approve jane
kubectl get csr jane -o jsonpath='{.status.certificate}' | base64 -d > jane.crt
kubectl config set-credentials jane --client-key=jane.key --client-certificate=jane.crt --embed-certs=true
kubectl config set-context jane --cluster=kubernetes --user=jane
```

:::ex
Tạo SA `ci` ở namespace `w5`. Cho nó quyền quản lý đầy đủ deployments và chỉ đọc pods trong `w5`. Kiểm tra 3 quyền: tạo deployment (yes), xoá pod (no), list pod ở `default` (no).
:::sol
```bash
kubectl create ns w5 ; kubectl create sa ci -n w5
kubectl create role ci-role -n w5 --verb='*' --resource=deployments.apps
kubectl create role ci-pods -n w5 --verb=get,list,watch --resource=pods
kubectl create rolebinding ci-rb -n w5 --role=ci-role --serviceaccount=w5:ci
kubectl create rolebinding ci-pods-rb -n w5 --role=ci-pods --serviceaccount=w5:ci
SA=system:serviceaccount:w5:ci
kubectl auth can-i create deployments -n w5 --as=$SA     # yes
kubectl auth can-i delete pods -n w5 --as=$SA            # no
kubectl auth can-i list pods -n default --as=$SA         # no
```
(Cũng có thể gộp 2 rule vào 1 Role bằng YAML.)
:::end

:::ex
Dùng ClusterRole có sẵn `view` để cho user `bob` quyền chỉ đọc **chỉ trong** namespace `w5`.
:::sol
```bash
kubectl create rolebinding bob-view -n w5 --clusterrole=view --user=bob
kubectl auth can-i list pods -n w5 --as=bob        # yes
kubectl auth can-i list pods -n default --as=bob   # no
```
ClusterRole + RoleBinding = quyền đó nhưng chỉ trong namespace của RoleBinding.
:::end

:::ex
Tạo user `jane` (group `devs`) bằng CSR như phần lý thuyết, cho group `devs` quyền list pods trong `w5`, và chạy `kubectl get po -n w5` bằng context của jane.
:::sol
Làm theo các bước CSR ở trên, rồi:
```bash
kubectl create rolebinding devs-pods -n w5 --clusterrole=view --group=devs
kubectl --context=jane get po -n w5        # OK
kubectl --context=jane get po -n default   # Forbidden
```
:::end

:::ex
Từ trong một pod dùng SA `ci`, gọi trực tiếp API liệt kê pod trong `w5` bằng curl và token được mount.
:::sol
```bash
kubectl run api-test -n w5 --image=curlimages/curl --overrides='{"spec":{"serviceAccountName":"ci"}}' -- sleep 3600
kubectl exec -n w5 api-test -- sh -c '
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
curl -s --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
  -H "Authorization: Bearer $TOKEN" \
  https://kubernetes.default.svc/api/v1/namespaces/w5/pods | head -20'
```
:::end

# L: Helm

Helm là trình quản lý gói cho K8s. Một **chart** là bộ template YAML + `values.yaml`. Cài chart tạo ra một **release**.

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm repo list
helm search repo nginx                     # tìm chart trong repo đã thêm
helm search repo bitnami/nginx --versions  # các version
helm show values bitnami/nginx > values.yaml
helm show chart bitnami/nginx

helm install web bitnami/nginx -n web --create-namespace \
  --set replicaCount=2 --set service.type=NodePort
helm install web bitnami/nginx -f my-values.yaml --version 18.1.0
helm list -A                               # mọi release
helm status web -n web
helm get values web -n web                 # giá trị đã đặt
helm get manifest web -n web               # YAML đã apply

helm upgrade web bitnami/nginx -n web --set replicaCount=3
helm upgrade --install web bitnami/nginx -n web    # cài nếu chưa có
helm history web -n web
helm rollback web 1 -n web
helm uninstall web -n web

helm template web bitnami/nginx --set replicaCount=2 > rendered.yaml   # chỉ render, không cài
helm pull bitnami/nginx --untar            # tải chart về thư mục
helm install web ./nginx                   # cài từ thư mục local
```
Cấu trúc chart: `Chart.yaml` (tên, version), `values.yaml` (mặc định), `templates/` (YAML có `{{ .Values.x }}`).
Chart OCI: `helm install x oci://registry-1.docker.io/bitnamicharts/nginx`.

:::ex
Thêm repo, cài chart nginx thành release `w5-web` ở namespace `w5-helm` với 2 replica và Service NodePort. Xác nhận có 2 pod.
:::sol
```bash
helm repo add bitnami https://charts.bitnami.com/bitnami && helm repo update
helm install w5-web bitnami/nginx -n w5-helm --create-namespace --set replicaCount=2 --set service.type=NodePort
helm list -n w5-helm
kubectl get po,svc -n w5-helm
```
:::end

:::ex
Nâng `w5-web` lên 3 replica, xem history, rồi rollback về revision 1.
:::sol
```bash
helm upgrade w5-web bitnami/nginx -n w5-helm --reuse-values --set replicaCount=3
helm history w5-web -n w5-helm
helm rollback w5-web 1 -n w5-helm
```
:::end

:::ex
Không cài vào cluster, render chart ra file `/root/web.yaml` với replicaCount=4, rồi đếm có bao nhiêu object kind Deployment trong file.
:::sol
```bash
helm template demo bitnami/nginx --set replicaCount=4 > /root/web.yaml
grep -c "^kind: Deployment" /root/web.yaml
```
:::end

:::ex
Tìm release nào trong cluster đang dùng chart `argo-cd` và ghi tên release cùng namespace vào `/root/argo.txt`.
:::sol
```bash
helm list -A | grep argo-cd
helm list -A | grep argo-cd | awk '{print $1, $2}' > /root/argo.txt
```
:::end

# L: Kustomize

Tuỳ biến YAML **không dùng template**: có một bộ `base`, các `overlays` (dev, prod) vá lên. Tích hợp sẵn trong kubectl.

```text
app/
├── base/
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   └── service.yaml
└── overlays/
    └── prod/
        ├── kustomization.yaml
        └── replicas-patch.yaml
```
```yaml
# base/kustomization.yaml
resources:
- deployment.yaml
- service.yaml
labels:
- pairs: {app: shop}
  includeSelectors: true

# overlays/prod/kustomization.yaml
resources:
- ../../base
namespace: prod
namePrefix: prod-
images:
- name: nginx
  newTag: "1.28"
patches:
- path: replicas-patch.yaml
configMapGenerator:
- name: app-config
  literals: [MODE=prod]

# overlays/prod/replicas-patch.yaml (strategic merge patch)
apiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 5
```
```bash
kubectl kustomize app/overlays/prod        # xem YAML sinh ra
kubectl apply -k app/overlays/prod
kubectl delete -k app/overlays/prod
```
- `configMapGenerator` sinh ConfigMap có hậu tố hash → đổi nội dung là pod tự rollout.
- Patch kiểu JSON 6902:
```yaml
patches:
- target: {kind: Deployment, name: web}
  patch: |-
    - op: replace
      path: /spec/replicas
      value: 3
```

:::ex
Dựng cấu trúc base (deployment `web` nginx:1.27 1 replica + service) và overlay `dev` (namespace `dev`, prefix `dev-`, 2 replica) và `prod` (namespace `prod`, image nginx:1.28, 4 replica). Apply cả hai và kiểm tra.
:::sol
```bash
mkdir -p kz/base kz/overlays/{dev,prod}
kubectl create deploy web --image=nginx:1.27 --dry-run=client -o yaml > kz/base/deployment.yaml
kubectl create svc clusterip web --tcp=80:80 --dry-run=client -o yaml > kz/base/service.yaml
printf "resources:\n- deployment.yaml\n- service.yaml\n" > kz/base/kustomization.yaml
cat <<EOF > kz/overlays/dev/kustomization.yaml
resources: [../../base]
namespace: dev
namePrefix: dev-
replicas: [{name: web, count: 2}]
EOF
cat <<EOF > kz/overlays/prod/kustomization.yaml
resources: [../../base]
namespace: prod
images: [{name: nginx, newTag: "1.28"}]
replicas: [{name: web, count: 4}]
EOF
kubectl create ns dev ; kubectl create ns prod
kubectl apply -k kz/overlays/dev ; kubectl apply -k kz/overlays/prod
kubectl get deploy -n dev ; kubectl get deploy -n prod -o wide
```
:::end

:::ex
Thêm vào overlay `prod` một ConfigMap sinh tự động `web-cfg` với `LOG=warn`. Xem tên thật của ConfigMap được tạo.
:::sol
```yaml
# thêm vào kz/overlays/prod/kustomization.yaml
configMapGenerator:
- name: web-cfg
  literals: [LOG=warn]
```
```bash
kubectl kustomize kz/overlays/prod | grep -A3 "kind: ConfigMap"
kubectl apply -k kz/overlays/prod ; kubectl get cm -n prod     # web-cfg-<hash>
```
:::end

# L: CRD, Operator và mở rộng API

## CustomResourceDefinition
CRD đăng ký **kiểu tài nguyên mới** với apiserver. Sau khi tạo CRD, bạn dùng kubectl với kiểu mới như mọi tài nguyên khác.
```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata: {name: backups.ops.example.com}     # <plural>.<group>
spec:
  group: ops.example.com
  scope: Namespaced
  names: {plural: backups, singular: backup, kind: Backup, shortNames: [bk]}
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              schedule: {type: string}
              retention: {type: integer}
```
```yaml
apiVersion: ops.example.com/v1
kind: Backup
metadata: {name: nightly}
spec: {schedule: "0 2 * * *", retention: 7}
```

## Operator
CRD chỉ lưu dữ liệu. **Operator** = CRD + **controller** theo dõi custom resource và thực hiện công việc (tạo pod, backup, failover…). Ví dụ: cert-manager (Certificate, Issuer), Prometheus Operator, tigera-operator của Calico, CloudNativePG.

## Lệnh hay dùng trong đề
```bash
kubectl get crd
kubectl get crd | grep cert-manager
kubectl api-resources --api-group=cert-manager.io
kubectl explain certificate.spec
kubectl explain certificate.spec.subject --recursive
kubectl get certificates -A
```

## Các thành phần mở rộng khác (khái niệm)
- **CNI** (mạng), **CSI** (lưu trữ), **CRI** (runtime) – 3 giao diện plugin của K8s.
- **Admission webhook**: dịch vụ ngoài được apiserver gọi để kiểm tra/sửa object.

:::ex
Tạo CRD `Backup` như trên, tạo resource `nightly`, rồi list bằng tên ngắn `bk`.
:::sol
```bash
kubectl apply -f crd.yaml
kubectl get crd backups.ops.example.com
kubectl apply -f nightly.yaml
kubectl get bk ; kubectl explain backup.spec
```
:::end

:::ex
Cài cert-manager (manifest chính thức). Ghi danh sách CRD của nó vào `/root/cm-crds.txt` và tài liệu trường `spec.issuerRef` của Certificate vào `/root/issuerref.txt`.
:::sol
```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
kubectl get crd | grep cert-manager > /root/cm-crds.txt
kubectl explain certificate.spec.issuerRef > /root/issuerref.txt
```
:::end
